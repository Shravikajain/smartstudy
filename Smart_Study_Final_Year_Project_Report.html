ABSTRACT

Students preparing for examinations often have to locate recurring topics across past papers, create additional practice questions and judge what to study next. Smart Study is a web-based learning application that brings these activities into one workflow. A student organizes work by subject and topic, uploads past examination papers in PDF format, and uses extracted text to identify question themes and recurring questions. The application can generate original multiple-choice or subjective practice questions from a selected topic and available study material. Its quiz service records responses and adjusts an ability estimate so that the next question is selected near the learner’s current estimated level. Learners can practise multiple-choice questions, subjective questions or both from a stored question bank. Subjective responses receive model-assisted scores and feedback together with an advisory estimate of whether the text was AI-written, and every test is saved so that answers, grades and feedback can be reviewed later. A separate authenticity check estimates AI-written content in learner-supplied notes or essays. An interview-practice workflow supports academic-subject or engineering-role sessions, typed responses and browser-recorded speech transcribed by a local Whisper model in the ML container. The system is implemented as a browser frontend, a Spring Boot API, a Python FastAPI machine-learning service and a PostgreSQL database, deployed together with Docker Compose. This report presents the problem, related learning systems, requirements, design, data model, implementation and test evidence. Fresh automated test runs (59 ML-service tests and 49 backend tests, all passing) and end-to-end runs against the deployed services are reported, together with a small evaluation showing that open AI-writing detectors identify text from a current language model only partially. Smart Study is a practice and revision aid, not a replacement for instructor judgment or an accredited examination platform. Its usefulness depends on the quality of uploaded material and generated feedback, and generated content should be reviewed by learners and instructors.

Keywords: adaptive learning, examination preparation, question generation, item response theory, past-paper analysis, interview practice, AI-generated text detection, self-evaluation.

CHAPTER 1
INTRODUCTION

1.1 Overview and Issues Involved

Past examination papers are valuable because they expose learners to the wording, topic emphasis and level of questions used in earlier assessments. In practice, however, a student may have to collect papers from several locations, read them manually, notice repeated concepts, prepare a personal question bank and then decide which question to attempt next. These steps are time-consuming and do not automatically provide targeted feedback. A static list of questions also gives every learner the same sequence even when their knowledge differs.

Smart Study addresses this workflow through a browser application organized around subjects and topics. Users can maintain their own subject areas, upload past papers, inspect recurring themes, generate new practice questions, take a quiz that selects questions according to an evolving ability estimate, and rehearse academic or engineering interviews. The system combines deterministic software components (storage, parsing, topic organization, quiz state and ability updates) with machine-learning services for text analysis, question generation, written feedback and speech transcription.

The application is designed as a study aid. Text extraction may be imperfect for scanned or poorly formatted documents; semantic clustering can group questions that share vocabulary without being conceptually identical; and generated questions or scores may contain errors. Consequently, the application should present its outputs as guidance and preserve the learner’s responsibility to verify educational content.

1.2 Problem Definition

University learners lack a single, account-based workflow that converts their own past-paper material into organized, recurring-topic insights and adaptive practice while also supporting written-answer feedback and interview rehearsal. Manual analysis is repetitive; static practice does not adapt to demonstrated performance; and separate tools often divide content management, practice and feedback across different interfaces.

Project objective. Design and implement a deployable web system that securely organizes study content, extracts and analyzes uploaded examination papers, generates topic-linked practice, adapts quiz difficulty from responses, and supports conversational interview practice with optional voice input.

Project objectives

  • Provide account registration, login and user-scoped access to subjects and study material.
  • Allow learners to create subjects/topics and upload PDF question papers with an optional examination year.
  • Extract text from digital PDFs and route scanned documents to a protected OCR service.
  • Group extracted questions and report recurring questions and topic clusters across papers.
  • Generate original multiple-choice and subjective questions and conduct adaptive quizzes.
  • Let learners choose multiple-choice, subjective or both question types when starting a test, and save every test for later self-evaluation.
  • Provide rubric-guided feedback for subjective answers and conduct subject/role interview sessions.
  • Estimate, as an advisory signal, whether subjective answers and learner-supplied material were written by AI.
  • Support browser audio capture and local-service transcription without sending interview audio to an external speech provider.

Scope and constraints

The implemented scope is a single-page browser interface, Spring Boot REST API, FastAPI ML service and PostgreSQL-backed storage, with Docker Compose as the local deployment route. The ML text-generation integration uses an Ollama-compatible endpoint configured through environment variables. Speech recognition uses Faster-Whisper in the ML container. A working provider key and configured services are required for model-backed features. No claim is made that the model outputs are guaranteed correct, that the system is a high-stakes assessment tool, or that the current repository represents a production-scale hosted service.

1.3 Proposed Solution

Smart Study uses a service-oriented design. The frontend presents sign-in, subject dashboards, paper management, practice, test-history, authenticity-check and interview views. The backend authenticates requests, checks ownership, persists domain data and coordinates calls to the ML service. The ML service exposes typed HTTP endpoints for analysis, question generation, grading, interview turns, AI-writing detection, scanned-PDF OCR and audio transcription. PostgreSQL stores structured entities; uploaded PDFs are kept in a persistent uploads volume. The system is composed with Docker so that its service boundaries and dependencies can be started together.

The paper-analysis pipeline extracts question-like text, normalizes vocabulary, creates TF-IDF features, combines them with MiniLM sentence embeddings so that reworded questions on the same topic can be grouped, and clusters questions using K-means. Candidate cluster counts are compared using the silhouette score within a configured bound. Similar questions across different papers are joined using TF-IDF cosine similarity and a configurable threshold; repeated concepts are returned with occurrence and year metadata. This produces an inspection aid rather than a guarantee of syllabus coverage.

Adaptive practice maintains an ability estimate for a quiz session. The implementation uses a logistic response probability and a bounded update after each answer, then selects a remaining question whose difficulty is closest to the current estimate. This is a simplified item-response-inspired procedure; it is not a calibrated psychometric instrument and does not estimate all parameters of a full item response model.

For self-evaluation, every test is stored with the learner’s answers. A learner can start a test limited to multiple-choice questions, subjective questions or both, and later reopen any past test to compare each answer with the correct option or the model answer and marking guide, together with the grade and feedback. Written answers also receive an AI-writing estimate from a locally run classifier. The same detector powers a standalone authenticity check for notes or essays, which reports an overall estimate and section-by-section scores. Because such detectors are imperfect (Section 4.3.4), the estimate is advisory and never changes a grade.

Figure 1.1: High-level study workflow. Generated and analyzed material returns to a learner-controlled practice and review loop.

Expected contribution

The project’s contribution is the integration of paper organization, recurring-question analysis, question generation, adaptive practice and interview rehearsal in one subject-centered application. Compared with static question lists, the quiz loop responds to prior answers; compared with standalone model prompts, the workflow stores user-owned topics, papers, questions and quiz sessions in a structured application. These are design-level advantages; comparative learning outcomes have not been established by a controlled educational study.

CHAPTER 2
LITERATURE SURVEY

2.1 Existing Solutions

Digital learning products commonly provide some combination of structured lessons, flashcards, assessment authoring, question banks and progress tracking. The following review compares representative tools and categories relevant to Smart Study. It is a functional comparison based on publicly described product capabilities, not a benchmark or independent evaluation of learning effectiveness.

2.1.1 Learning management systems and Moodle Quiz

Moodle is an open-source learning management system used to deliver course content, activities and assessments. Its Quiz activity supports instructor-authored questions, attempts, grading and feedback within a course [6]. It is a capable platform when an institution configures the course and question bank. Smart Study differs in its focus on an individual learner’s past examination papers, automatic cross-paper topic/repetition analysis and adaptive practice workflow. Moodle’s extensive administration model may be more than a learner needs for personal revision.

2.1.2 Quizlet

Quizlet centers on user- or teacher-created study sets and offers digital flashcard and practice experiences [7]. Its strength is quick vocabulary and concept review supported by a large content ecosystem. A user typically needs prepared study material; it does not constitute the project’s specific pipeline for parsing a learner’s examination-paper collection, clustering paper questions and using those patterns to seed topic-linked adaptive quiz sessions.

2.1.3 Khan Academy

Khan Academy provides structured lessons and practice across supported subjects, with learner progress linked to a curated curriculum [8]. Its strength is the combination of instructional material and exercises. Smart Study is instead designed to start from a learner’s own examination papers and topic organization. It does not attempt to reproduce Khan Academy’s broad curriculum, instructional video library or institution-scale learning analytics.

2.1.4 Commercial exam-preparation platforms

Exam-preparation services commonly provide syllabus-aligned courses, mock examinations, question banks and performance reports for particular examinations. Their curated content can provide consistency and exam-specific guidance. Their scope is often tied to a provider’s content catalog and target assessment. Smart Study’s intended distinction is learner-supplied paper analysis and customizable subjects rather than a centrally curated, examination-specific question bank.

2.1.5 AI study assistants and question generators

General-purpose AI assistants and educational question generators can create explanations, practice prompts and conversational feedback. They offer flexible interaction but depend on the supplied context and the model’s reliability. A standalone chat does not automatically provide a persistent relation between a learner’s subjects, uploaded papers, generated question records, quiz state and past-paper recurrence. Smart Study wraps model services in a structured subject-and-quiz workflow and validates generated question fields before storing them.

2.1.6 Speech-enabled interview practice

Interview simulators and voice assistants can help candidates rehearse responses. Smart Study’s interview workflow supports subject or engineering-role targets, question sequences and feedback; the browser can capture audio and submit it to the local ML service for transcription. This is a focused practice workflow, not a hiring assessment, professional interview credential or guarantee of interview performance.

2.1.7 AI-generated text detectors

Detectors of AI-generated text are commonly trained as classifiers on pairs of human-written and model-written text. A widely used early example was trained on the HC3 corpus of human and ChatGPT answers [16]. Such supervised detectors tend to generalize poorly to text from newer models, and they have been shown to misclassify writing by non-native English speakers as AI-generated [17]. More recent open detectors, such as Fakespot’s RoBERTa model [18], are trained on output from a wider range of models. Smart Study uses a detector of this kind to give learners a reflective signal about their own writing, presents it as a probability with explicit uncertainty, and does not use it for grading.

Research concepts informing the project

Item response theory models the probability of a response in relation to learner ability and item properties. The project borrows the intuition that practice can be selected near an evolving estimate of ability, while implementing a deliberately simpler bounded logistic update [1, 2]. TF-IDF assigns greater importance to terms that are informative within a document collection, while K-means groups vector representations around centroids [3, 4]. The silhouette coefficient can help compare candidate clusterings by considering compactness and separation [5]. Sentence embeddings represent a whole sentence as a dense vector so that sentences with similar meaning lie close together even when they share few words [19]; the compact MiniLM family makes this practical on a CPU [20]. These techniques are used as practical analysis components; none alone understands educational semantics or proves that a cluster is pedagogically coherent.

Gap and justification. The reviewed systems typically emphasize curated courses, flashcard sets, instructor-managed assessments or open-ended generative chat. The project addresses a narrower integration gap: a learner can bring their own paper corpus, organize it by subject, inspect recurring patterns and continue directly into generated and adaptive practice, with interview rehearsal in the same application. The gap is functional and architectural; user studies are still required to demonstrate learning benefit.

2.2 Methodology and Conceptual Requirements

2.2.1 Development methodology

The project follows an iterative implementation approach. First, the repository’s user-facing workflow and domain objects are defined. Next, API contracts and persistence entities are implemented in the Spring Boot service. The Python service supplies analysis and model-backed tasks behind typed request/response schemas. The browser interface consumes the API, while Docker Compose connects the application and database. Automated unit, integration and API tests are used to check important behaviors. Iterations address the paper-import path, adaptive quiz lifecycle, interview turn flow and voice transcription. Later iterations added question-type selection, stored test history and AI-writing detection, and hardened the language-model integration after live testing against the hosted model. Configuration values and secrets are supplied through environment variables rather than committed source.

2.2.2 Concepts and algorithms

  • REST service: An HTTP API exposes resources and actions using JSON or multipart form data. The frontend communicates with the backend; the backend calls the internal ML service.
  • PDF extraction and OCR: PDFBox extracts embedded text from digitally generated documents. When scanned pages contain no usable text, an authenticated internal endpoint can render pages and run OCR. Extraction quality depends on document clarity and language support.
  • TF-IDF: Each question is represented by weighted one- and two-word terms. Frequent general examination words are removed to reduce uninformative similarity.
  • Sentence embeddings: Each question is also encoded with the all-MiniLM-L6-v2 model (mean-pooled and L2-normalized, pinned revision). For clustering, the TF-IDF and embedding vectors are joined with weights of 0.4 and 0.6, so cosine similarity reflects both shared wording and meaning. In a calibration on sample algorithm questions, the embeddings scored the reworded pair “N-Queens” / “8 queens puzzle” at 0.66 where TF-IDF scored 0.16, but also scored two different shortest-path questions at 0.62; recurring-question detection therefore remains on TF-IDF. If the embedding model is unavailable or still loading, clustering falls back to TF-IDF alone.
  • K-means and silhouette selection: K-means groups the combined text vectors. The analysis chooses a cluster count by checking silhouette scores for a bounded set of candidates; deterministic random seeds make the process more reproducible.
  • Cosine similarity and repeated questions: Questions whose TF-IDF cosine similarity exceeds a threshold are linked only across different paper IDs. Connected groups supply the repeated-question list and years.
  • Adaptive quiz: A logistic probability estimates the chance of a correct response given ability and difficulty. After an answer, the estimate is updated by a diminishing step and clamped to a supported range. The next eligible item is the one closest to the current estimate.
  • Structured generation and feedback: The ML service requests schema-constrained JSON. In live testing, the hosted model (gpt-oss:120b on Ollama Cloud) did not enforce the requested schema: it returned bare lists, renamed fields or Markdown. The service therefore also states the schema in the prompt, parses replies leniently, maps common alternative field names, retries once on malformed output, shuffles multiple-choice options so the correct answer’s position varies, and discards duplicate prompts or options before validating question type, option count, correct-answer index and reference answer. Subjective feedback is model-assisted and should be treated as formative feedback.
  • AI-writing detection: Text is split into overlapping 512-token windows and classified by fakespot-ai/roberta-base-ai-text-detection-v1 (pinned revision). Window probabilities are averaged and the text is flagged at 0.60. The interface reports three bands: below 35% likely human-written, 35–60% uncertain, and 60% or above likely AI-written. Long documents also show the score of each window.
  • Background model loading: The detector, Whisper and embedding models load on background threads at start-up. A request that arrives first never waits for a download: clustering falls back to TF-IDF, and detection or transcription report that the model is still loading.
  • Speech transcription: The browser records an audio response and sends it to the internal API. Faster-Whisper performs local CPU transcription in the ML container; the resulting text is submitted as the candidate response.

2.2.3 Security and privacy considerations

Authenticated application routes use JWT-based identity and user ownership checks. All ML-service endpoints except the health check are protected by a shared internal service key and constant-time comparison. Deployment secrets, database credentials and model-provider keys are configured externally. Uploaded papers and audio contain potentially sensitive information, so operators should restrict access to volumes, use HTTPS outside localhost, establish retention rules, and avoid uploading material without the right to use it. Model providers may process text sent for generation or grading; operators must review provider terms and avoid sensitive personal data. The local transcription path is designed not to send captured interview audio to an external speech provider. The authenticity check stores only the source name, character count and scores; the submitted text is not persisted. Because AI-writing detectors can wrongly flag human writing, including that of non-native English writers [17], the application labels its estimate as advisory and never uses it for grading.

3.1.2 Non-functional requirements

  • Security: User-owned data must be checked against the authenticated principal; internal ML endpoints must not be exposed as public application routes.
  • Reliability: Invalid PDF, malformed model responses and unavailable dependencies must produce explicit errors rather than fabricated success results. Model downloads happen in the background so that requests are not blocked, and grading continues without an AI estimate if the detector is unavailable.
  • Usability: Primary workflows must be available in a modern browser, with typed answers retained as an alternative to voice. Nginx asks browsers to revalidate the application files on each load so that updates take effect immediately.
  • Transparency: AI-writing estimates are shown as probabilities with an uncertainty band and a statement that they are not proof of authorship.
  • Maintainability: Frontend, API, ML service and persistence responsibilities are separated and communicate through explicit contracts.
  • Portability: Dockerfiles and Docker Compose describe the local multi-service deployment; secrets and runtime configuration remain external.
  • Performance: File-size and question-count limits bound expensive operations. Exact throughput and latency targets have not yet been established by load testing. Slow ML calls (OCR, detection, grading and generation) run outside database transactions, with open-session-in-view disabled, so a request does not hold a database connection while it waits.
  • Data integrity: Relational ownership and foreign-key associations keep each subject, paper, topic and quiz connected to its user context.

3.2 Hardware Requirements

Development/deployment host (minimum practical baseline): 64-bit Windows, macOS or Linux capable of running Docker Desktop/Engine; a multi-core CPU; 8 GB RAM for a small local trial (16 GB or more recommended when PostgreSQL, the Java service and the local models run together); several GB of free disk for images, uploaded papers and the downloaded local models (about 500 MB for the AI-writing detector, 90 MB for the sentence-embedding model and 145 MB for the Whisper base model); and a microphone for voice practice. On slow connections the first model download can take a long time; the models are cached in a Docker volume and can be pre-seeded from an existing Hugging Face cache. The exact memory and disk requirement depends on the chosen Whisper model, OCR packages and concurrent workload.

Client device: A recent laptop, desktop or mobile device with a standards-compliant browser and network access to the application. Microphone access requires a secure context such as localhost or HTTPS and explicit browser permission. If the client microphone is unavailable, interview answers can be typed.

External services: The configured Ollama endpoint and model must be reachable for question generation, grading and conversational interview responses. When using a hosted provider, a valid API key is required. These are operational dependencies, not hardware requirements of the learner’s browser.

The learner initiates all primary use cases. 3.3.2 Use Case Descriptions (Rational Unified Process Style)

UC-01 — Register or Sign In

Primary actor: Learner. Preconditions: Application is reachable; learner has a valid email and password for the selected action. Trigger: Learner submits the registration or login form. Main flow: (1) System validates required fields. (2) For registration, the service creates the account if the email is not already in use; for login, it verifies credentials. (3) On success, the service issues an authentication token and the client opens the subject dashboard. Alternatives: Invalid fields, duplicate email or rejected credentials return an error and leave the user unauthenticated. Postconditions: Successful authentication establishes the user context for subsequent requests.

UC-02 — Create Subject and Topic

Primary actor: Authenticated learner. Preconditions: Valid authenticated session. Trigger: Learner submits a subject or topic form. Main flow: (1) Client sends the name and related parent identifier. (2) Backend validates the request and confirms parent ownership. (3) Backend stores the new record and returns it to the client. Alternatives: Missing/invalid names or a resource owned by another user are rejected. Postconditions: The subject/topic is available within that learner’s workspace.

UC-03 — Upload and Analyze Past Papers

Primary actor: Authenticated learner. Preconditions: Learner owns a subject; input is a supported PDF within configured upload limits. Trigger: Learner uploads a paper and optionally supplies its year. Main flow: (1) Backend verifies subject ownership and stores the file under a generated name. (2) Text is extracted from the PDF; if the normal extraction path yields no usable text, the configured OCR flow may be used. (3) Paper metadata and text are associated with the subject. (4) On analysis request, extracted questions are normalized, vectorized, clustered and compared across papers. (5) Cluster and recurrence results are returned. Alternatives: Invalid PDF, unreadable scan, no papers or unavailable ML service produce an explicit error. Failed upload processing removes the newly stored file where possible. Postconditions: A successful upload is attached to its subject; analysis is returned without changing the source paper.

UC-04 — Generate Practice Questions

Primary actor: Authenticated learner. Preconditions: Learner owns a subject and has selected one or more topics. Trigger: Learner requests a practice set. Main flow: (1) Backend composes a typed generation request with subject, topics, requested question type and optional paper context. (2) ML service requests structured output from the configured language model. (3) Response fields and question-specific rules are validated. (4) Usable questions are stored against their topic and returned. Alternatives: Provider unavailable, malformed output or no valid questions are reported as failure; invalid model items are not silently presented as questions. Postconditions: Valid questions are available for later practice.

UC-05 — Complete an Adaptive Quiz

Primary actor: Authenticated learner. Preconditions: Learner owns the subject; a usable question pool exists. Trigger: Learner chooses multiple-choice, subjective or both and a question count, then starts a test. Main flow: (1) Backend filters the subject’s question bank by the chosen type, creates a quiz session and selects the initial question. (2) Learner submits an answer. (3) Backend records correctness, updates ability and answer counts, and chooses the next question closest to current ability. (4) System returns answer feedback and progress. (5) Session ends at its configured maximum or when no questions remain. Alternatives: An invalid session/question/answer is rejected; if no question of the chosen type exists, the learner is told to generate some first. Subjective answers are graded and checked for AI-writing outside the database transaction (Figure 3.4); if the detector is unavailable the answer is graded without an estimate. Postconditions: Completed session records its status, counts, final estimate and timestamps, and every answer is retained for later review.

UC-06 — Practice an Interview

Primary actor: Authenticated learner. Preconditions: Interview service and, for voice, browser microphone permission are available. Trigger: Learner chooses a subject or engineering role, level and question count. Main flow: (1) Client requests the next interview turn with prior conversation context. (2) ML service returns a question. (3) Learner types or records an answer. (4) Recorded audio is sent through the protected transcription route; transcription text becomes the answer. (5) Service evaluates the answer and returns feedback/score or the next question. (6) Session completes at the selected limit. Alternatives: Microphone denial or transcription failure leaves text entry available; service errors are displayed. Postconditions: Learner receives session feedback; browser audio is not sent to an external speech provider by this design.

UC-07 — Review Past Tests

Primary actor: Authenticated learner. Preconditions: Learner has answered at least one question in a test. Trigger: Learner opens My tests. Main flow: (1) Backend lists the learner’s tests with subject, date, question type, score, average written score and the number of answers flagged as likely AI-written. (2) Learner opens a test. (3) Backend returns each answered question with the learner’s answer, the correct option or model answer and marking guide, grade, feedback and AI-writing estimate. Alternatives: A test owned by another user is refused; tests taken before history was recorded open without the newer fields. Postconditions: No data is changed.

UC-08 — Check Material Authenticity

Primary actor: Authenticated learner. Preconditions: AI-writing detector is loaded. Trigger: Learner pastes text or uploads a PDF, .txt or .md file. Main flow: (1) Backend extracts text (PDFs use the normal extraction and OCR path) and checks it is between 50 and 60,000 characters. (2) ML service scores overlapping 512-token windows and returns the overall and per-window probabilities. (3) Backend saves the result summary and returns the full result. (4) Interface shows the overall band, the section-by-section scores and the learner’s recent checks. Alternatives: Both inputs, unsupported file types, too-short or too-long text, or a detector that is still loading produce a clear error. Postconditions: A result summary is stored; the checked text is not.

4.1 Database Design

The backend uses JPA entities mapped to relational tables. The following ER view summarizes the core relations implemented in the domain model. A learner owns subjects; subjects contain topics and uploaded papers; topics contain questions; quiz sessions refer to a learner and subject and maintain a question pool; answers link a session to the question answered and keep the written answer, grade, feedback and AI-writing estimate for later review; authenticity checks belong to a learner. Question options are persisted as an ordered element collection. The many-to-many question pool is represented by a join table.

The diagram below shows the central domain and service classes rather than every framework DTO, repository and configuration class in the codebase. It reflects the project’s main responsibility boundaries.

Figure 4.2: Core domain classes and coordinating services. QuizHistoryService reads the sessions and answers recorded by QuizService; written answers and authenticity checks both use the ML service’s AI-writing detector.
Class / component Purpose and principal behavior
User JPA entity for account identity. Holds ID, email, credential value and full name; forms the ownership root for user-specific subjects and quiz sessions.
Subject JPA entity representing a learner’s study area. Associates to an owner and contains topics.
Topic JPA entity representing a named topic and optional description within a subject.
QuestionPaper JPA entity holding source filename, stored filename, exam year, upload timestamp, extracted text and owning subject.
Question JPA entity for a practice prompt, ordered options, answer metadata, question type, explanation, difficulty and topic. It increments the number of answers and exposes question-type-aware accessors.
QuizSession JPA entity that records learner, subject, maximum question count, progress, ability estimate, current question, status, question pool, chosen question types and start/finish times. `recordAnswer` updates counters/ability; `finish` closes the session and records the completion time.
QuizAnswer JPA entity linking an answer to its session and question, retaining the selected option, correctness and ability before/after the response; `recordWrittenAnswer` adds the written text, grade, feedback and AI-writing estimate. An earlier version stored the correct option in place of the learner’s selection; this was corrected and is covered by a unit test.
IrtEngine Stateless utility. `probabilityCorrect(ability, difficulty)` evaluates a logistic response probability; `information` returns p(1-p); `updateAbility` and `updateDifficulty` apply bounded diminishing-step updates; `selectNext` selects the candidate closest to estimated ability.
QuestionPaperService Coordinates ownership validation, generated filename storage, PDF text extraction, persistence, listing, re-extraction when text is missing and deletion. It cleans up a newly stored file when upload processing fails.
SubjectAnalysisService Loads a user’s subject papers, verifies readable text, maps data to the ML request and returns timestamped analysis metadata.
QuizService Starts tests, optionally filtering the question pool to multiple-choice or subjective questions, and records answers. For a written answer it reads the question in one short transaction, calls the detector and grader with no transaction open, then stores the result in a second transaction (TransactionTemplate).
QuizHistoryService Lists a learner’s tests with summary scores, builds the per-question review of one test after an ownership check, and counts the subject’s multiple-choice and subjective questions for the practice picker.
AuthenticityService / AuthenticityController Accepts pasted text or a PDF, .txt or .md file, validates its length, calls the detector, saves the result summary and returns the overall and per-section scores; also lists the learner’s 20 most recent checks.
ML service (`analyzer`, `embeddings`, `llm_client`, `ai_detector`, `background`) Python modules split and normalize questions, build TF-IDF and sentence-embedding features, cluster and identify recurring text. The language-model client generates typed questions (with lenient parsing and field mapping), grades subjective answers and manages interview turns. `ai_detector` scores 512-token windows for AI-written text; `BackgroundLoader` loads local models on background threads so requests never wait for a download.

4.3.4 AI-writing detector evaluation

To check whether the AI-writing estimate is meaningful for current language models, eight answers were generated with gpt-oss:120b (four in an exam style and four in a casual student voice, on topics such as Dijkstra’s algorithm, TCP and photosynthesis) and compared with eight human-written passages taken from Python standard-library documentation. Each detector’s AI probability was compared with the 0.60 flag threshold.

Detector AI texts flagged (of 8) Human texts wrongly flagged (of 8) Model size
Hello-SimpleAI/chatgpt-detector-roberta (2023, previously used) 0 0 about 500 MB
fakespot-ai/roberta-base-ai-text-detection-v1 (2025, adopted) 3 2 499 MB
MayZhou/e5-small-lora-ai-generated-detector 2 4 133 MB

The original detector, trained on 2023 ChatGPT answers [16], did not flag any of the eight current-model answers: every AI sample scored below 4%. The Fakespot model was adopted because it detected the largest share of AI text while wrongly flagging fewer human passages than the e5-small model. On a 7,260-character document mixing three human passages and four AI answers, it rated one AI-written section at 68% and flagged none of the human sections, but it rated another AI-written section at only 34%. Its output can therefore be wrong in both directions, which is why the application presents it as an advisory estimate. Sixteen samples are too few for reliable accuracy figures, and documentation prose differs from student writing; a larger evaluation is listed as future work.

CHAPTER 5
CONCLUSION

5.1 Conclusion

Smart Study demonstrates an integrated web application for organizing examination preparation around learner-supplied subject material. Its implemented workflow connects account-scoped subjects and topics, PDF paper ingestion, question and recurrence analysis, generated practice, adaptive tests by question type, stored test history for self-evaluation, subjective feedback with an advisory AI-writing estimate, a standalone authenticity check and interview rehearsal. A Java API coordinates persistent domain operations, while a Python ML service isolates text analysis, language-model interaction, OCR and speech transcription. Docker Compose describes a repeatable local multi-service deployment.

The project also demonstrates how a simple ability estimate can influence practice selection. The implemented logistic update and nearest-difficulty selection make quiz sessions responsive to learner answers, while remaining intentionally simpler than a fully calibrated item-response assessment. Fresh automated runs on 26 October 2026 passed all 59 ML-service tests and all 49 backend tests, and end-to-end runs against the deployed services confirmed question generation, adaptive practice, written-answer grading, test review, the authenticity check and voice transcription. Live testing also exposed real problems that were then fixed: the hosted model ignored the requested JSON format, first-time model downloads could block requests, and the original AI-writing detector flagged none of the current-model answers. These results support important implementation paths; they do not establish educational effectiveness, model accuracy, accessibility compliance, load capacity or production readiness.

The main practical value is workflow integration rather than a claim that automated generation or clustering is inherently superior to instructor-authored learning. Uploaded paper quality, correct user configuration, reliable model responses, review of generated items and secure operations remain necessary. Wider use would require verifying the deployment with an approved model-provider configuration, adding explicit authorization and failure-path tests, and reviewing the quality of generated questions with educators.

5.2 Limitations

  • Clustering combines TF-IDF with MiniLM embeddings, which groups reworded questions better but can still merge different questions on a shared topic. Recurring-question detection uses TF-IDF only and may miss paraphrases. Cluster labels are descriptive terms, not validated syllabus topics.
  • AI-writing detection is unreliable: in a 16-sample evaluation the adopted detector flagged 3 of 8 AI-written answers and wrongly flagged 2 of 8 human passages. Its estimate must never be treated as proof, and the sample is too small to give a dependable accuracy figure.
  • The hosted language model did not enforce the requested JSON schema; the service compensates with prompting, lenient parsing and validation, but some generated items may still be discarded and a request can fail.
  • Question generation and subjective grading depend on an external language model and can be incorrect, inconsistent or biased.
  • The adaptive algorithm is a simplified pedagogical heuristic; it has not been calibrated on a representative learner/item dataset.
  • OCR accuracy varies with scan quality, layout and language; extraction should be inspected before relying on results.
  • No controlled learner study, formal accessibility review, production load test or availability evaluation is included in the current evidence.
  • The current local deployment requires operator-provided secrets, database setup and model-service configuration. The local models total about 735 MB and can take a long time to download on slow connections.

5.3 Future Scope

  • Conduct educator and learner evaluation; measure task completion, usefulness, question quality and learning outcomes.
  • Add instructor review/approval workflows and citations to the uploaded source passages behind generated questions.
  • Calibrate embedding thresholds on a larger labelled set before extending embeddings to recurring-question detection, while retaining transparent thresholds and human review.
  • Evaluate AI-writing detection on a larger, consented set of student answers; compare stronger detectors and report uncertainty for each section.
  • Use the saved test history to show progress over time for each topic.
  • Evaluate calibrated IRT models using sufficient response data, item calibration, uncertainty estimates and privacy-preserving analytics.
  • Add versioned database migrations, retention controls, backups, accessibility testing, security assessment and operational monitoring.
  • Support more document types and languages after measuring extraction accuracy and defining data-handling requirements.

APPENDIX A — USER WORKFLOW AND API SUMMARY

A.1 Suggested demonstration workflow

  1. Start the services using the Docker Compose instructions in the project README and provide locally generated secrets and model-provider configuration.
  2. Register a demonstration account and create a subject and topic.
  3. Upload a legally usable sample question-paper PDF and verify its extracted text and year.
  4. Run analysis and inspect clusters and recurring questions against the original paper.
  5. Generate a practice set; review generated questions for correctness before attempting them.
  6. Take a short quiz and observe feedback and question progression.
  7. On the subject page, start a test from the question bank with a chosen question type (multiple choice, subjective or both). Answer one subjective question and note the grade, feedback and AI-writing estimate.
  8. Open My tests, select the test and review each answer against the correct option or the model answer.
  9. Open Authenticity check, paste a passage or upload a PDF/.txt/.md file, and inspect the overall estimate and section scores; explain that the result is advisory.
  10. Run a typed interview session. If using voice, grant microphone permission and verify transcription before submitting the answer.
